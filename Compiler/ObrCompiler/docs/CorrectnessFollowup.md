# 私有地址与别名分析修复（2026-10-31）

本轮仅处理 ObrCompiler 需求中的正确性与验证缺口。以下结果属于原产品基线 `7bf7887` 上的编译器检查点；本轮发现上游已推进至 `28ae11e`，合入该上游后的实现必须重新验证，不能沿用这里的运行或性能结论。PR 仍应保持 Draft。

## 修复的具体问题

原前向分析把“地址最初来自私有区”当成“运算后的地址仍是私有区”，也把重定位来源不同当成不可能别名。地址经运算移到共享区后，重复读取可能被消除；两种来源最终指向同一字时，第二次写入 9 后，读取还可能使用第一次写入的 7。

独立审查又发现两种相邻情况：运行时装入的帧指针没有可用的实际范围证明；从帧指针字窄加载，只得到低位，不能继承完整指针的私有性。合法对齐的 `kStack+53248` 低 16 位为 4096，提供了具名反例。

最终规则如下：

- 来源分类不是互斥地址空间，无法证明不重叠时保守使旧事实失效。
- 只有已知数值地址且整个访问区间落在私有栈区时，才消除间接读取。
- 符号帧/栈指针保留地址关系以供失效分析，但不再仅凭其来源授予私有转发资格；窄加载同样不授予。
- 地址运算越出私有区、访问宽度跨过上界时撤销资格；刚好结束于上界的完整 64 位访问仍可转发。

这些改动是保守收紧，可能降低转发收益。没有修改语言、CPU、内核、协议、镜像版本或布局常量。

## 与 native fault 分开处理

本轮在 Chrome 使用原 v5 观察器做了四组内核单因素对照，其余程序与固件均固定为原 O1 产物，仅替换 kernel/start：

| 内核编译选项 | 最后已观察公开快照出现新增 native fault | 管道结果 |
|---|---|---|
| 原 O1 | 是 | 超时 |
| O1 -fno-native-compact | 否 | 超时 |
| O1 -fno-peephole | 是 | 超时 |
| O0 | 否 | 超时 |

四组均有完整 producer barrier，但原观察器仍只每250ms在fault数量改变时上报，不能据此证明结束瞬间新鲜度。这里的“否”仅指最后已观察快照。另有16组普通 Obr 程序，覆盖立即数边界、八个参数位置及紧凑/原编码形态的黑盒返回值和 ABI，全部通过；有限例子不能证明所有 native 编码正确。

这把原故障的触发范围缩小到 native 紧凑编码或其造成的布局变化，不能推出编码本身有语义错误。四组仍共同超时，也没有证明内核装入地址与堆池冲突的完整运行时因果链。本次别名修复不关闭该 native fault、历史 Starting、NAS 原始差异或全部 MUST。

个人目的：修复有具体反例的编译器错误，并保留独立审查、修订、失败和最终计量的身份边界，便于维护者逐项核对。

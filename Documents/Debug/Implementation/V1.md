# v1 交付合同

> 这是 `Implementation/` 层的 v1 范围，不是最终能力上限。
> v1 的目标是：研发团队可以独立启动一次采集、拿到可复现的原始记录和文本报告、按标准判断哪些已覆盖、哪些未覆盖。

## 2. v1 验收

在仓库根执行：

```powershell
cd Toolchain
npm run check
npm test
cd ..
node Documents\Debug\Tools\ztrace.mjs --chrome "<浏览器可执行文件>" --command "id" --command "pwd" --command "sleep 3" --out dev\Debug\ztrace-acceptance --key-delay 100 --timeout 30000
node Documents\Debug\Tools\ztrace-check.mjs --file dev\Debug\ztrace-acceptance\capture.json
```

`--chrome` 只在 headless Chrome 没有 WebGPU 适配器时使用；默认自动查找 Chrome/Edge。Edge 路径按本机安装位置替换。

通过条件：

1. `npm run check` 无错误。
2. `npm test` 输出 `consistency ok`。
3. `ztrace.mjs` 退出 0，写出 `capture.json`、`report.txt`、`capture.log`。
4. `ztrace-check.mjs` 输出 `ztrace-check ok`。
5. `capture.json` 的 `schema` 是 `zeros.ztrace.capture/1`，含 `git`、`environment`、`sourceMaps`、`boot`、`commands`。
6. 每条成功命令有 `status`、`report`、`entries`、`faults`；`boot` 也有 `status`、`report`、`entries`、`faults`；`entries` 的字段是数字。
7. 报告里能看到 `task waits` 或 `task sleeps`（有真实阻塞时）以及 `input spans: matched=...`。
8. 采集不修改 `boot/debug`，不生成 `.debug`。

## 3. 输入关联的边界

v1 的 `input spans` 是**页面按键 → 客侧 key ring 消费**的区间，使用 ZKP1 第 7 字的唯一关联号：

- 页面为每个按下的键生成一个 16 位关联号，放进 ZKP1 事件第 7 字；`Input` 的 `A0` 是这个号，`A1` 是键值。
- 设备保存关联号，查询码 `7` 原样返回。固件在 `poll` 里读回，`keyOffer` 把它放进 key ring packed 字的高 32 位；低 32 位的键值和修饰位不变，内核终端不读高 32 位。
- 主板在 key ring 次数增加时读 packed 字的高 32 位，发 `KeyConsumed`（`A0` 是关联号，`A1` 是键值）。报告按 `A0` 精确配对，不再按键值/顺序猜测。
- `keyup` 不产生客侧消费，也不记 `Input`。
- 固件扫描键盘口时按 `ZKP1` 匹配；设备也用 `ZKP1`。版本标识回退后两边一致，不会因标识不匹配在 `bios` 直接 `halt()`。

`Keys.obr` 在写 key ring 次数之前会写一次 6592。这格在次数 6528 和槽 6656 之间，地址记在 `Bios.obr`。没有这次写，槽数据和次数可能以错误顺序对监督核可见，终端会收不到按键。这是输入可靠性前提，不是可选优化。任务诊断字在 4416，不占用引导探针 7296。

鼠标的 `pointer spans` 只覆盖 BIOS 设置页；普通 shell 没有指针消费者。ZPP1 设备本身实现了第 7 字关联号和查询码 `10`，但 v1 不声称“鼠标到 shell 指针”的端到端。

## 4. 明确不在 v1

这些能力没有在 v1 里伪装成完成：

- core 7 外部命令的按任务源行映射。
- 完整逐指令环。
- 宿主 JS profiler / Worker 内部队列深度。
- 显示/GPU 的捕获/合成/accel 分阶段拆分。
- 全 54 条命令的完整长跑回归；批次 2/4 仍有命令超时。

它们需要独立 ring、profiler 或更长的语料运行；不能在当前宿主侧约束里严谨完成。

## 5. v1 的价值

- 任何研发人员不依赖 `dev/` 本地脚本，直接用 `Documents/Debug/Tools/ztrace.mjs` 采集。
- 采集结果是版本化 JSON：能看原始记录、文本报告、git/环境/源行表状态。
- 报告先给树，再给服务总量、等待、任务 sleep/wake、输入区间、协议、worker、内存和拒绝；未覆盖项明确写出。
- 关闭开关、超时、无表、空采集都有明确行为。
- 任何新观测点都必须按 `Standard/Instrumentation.md` 和 `Points.md` 更新，避免“加了但没人知道”。

## 6. 维护

- 改变 `capture.json` 字段或 schema：更新本文件、`Runbook.md`、`Observability.md`。
- 改变事件码/记录布局：更新 `Observability.md`、`Points.md`、`TraceReport`。
- 改变 v1 边界：先在本文件写明新范围，再改实现；不能把 v2 能力静默算进 v1。

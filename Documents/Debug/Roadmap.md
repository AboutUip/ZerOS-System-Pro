# ZTrace 能力路线图

> 当前交付：**ZTrace v1.1**（2026-11-02）。v2 P4 进行中；完整计划在 `dev/Plan/ZTrace-v2.md`，v1.1 交付计划在 `dev/Plan/ZTrace-v1.1.md`。

## 1. 目标

建立一套可复用的调试能力：任意子系统、任意路径都能按同一套标准被观察、定位、验证和回归。

不是完成某次性能专项，也不是让某组命令变快。命令、测试程序和故障注入都只是验证语料。

## 2. 判断标准

一项能力算完成，需要同时满足：

- **广度**：目标层的生命周期、边界、错误路径都有检测点，或明确标为未覆盖。
- **深度**：能从决策层下钻到执行层和因果层，不是只有总数。
- **可验证**：已知答案、边界、关闭、溢出、跨线程、开销都有测试。
- **可复现**：记录带版本、环境、开关、样本和原始数据。
- **可维护**：schema、命名、覆盖矩阵和实现同步更新。

## 3. 能力支柱

### 3.1 标准与治理

当前：

- 方法、证据、观测设计、实验设计已分层。
- 实现说明与标准分离。一次实验的原始输出不进入文档目录。

下一步：

- 为标准补检查表：实验评审、观测点评审、报告评审。
- 建立 schema/事件命名版本规则。
- 把「标准是否被遵守」变成可检查项，而不是靠记忆。

退出：

- 新观测点必须过 `Standard/Instrumentation.md` 清单。
- 新实验必须过 `Standard/Experiments.md` 模板。
- 实验结论必须能给出 E3 或 E4 等级。等级写在当次输出里，不另建文档记录。

### 3.2 宿主边界广度

目标层：

- CPU、内存、主板、扩展口、NAS、GPU、显示、键盘、鼠标、沙盒、时钟、探针。
- 页面、Worker、消息、协议、共享内存。

当前：

- CPU 系统调用/命令/安装/调度取走/停机快照、NAS 端口、GPU 呈现/阶段、内存按核/服务、宿主事件已有检测点。
- 时钟、宿主 JS、显示帧阶段、鼠标 shell 消费、沙盒语义、协议字节分布仍未完整；键盘 ZKP1 唯一关联已接。

下一步：

- 按层补生命周期、边界、错误点；先补没有点的子系统。
- 每个设备至少回答：请求、传输、设备处理、回复、失败。

退出：

- 覆盖矩阵中目标层不再有「无检测点」。
- 每个点有已知答案和关闭测试。

### 3.3 执行深度

层级：

1. 计数：执行条数、批次、字节。
2. span：操作耗时。
3. 采样：热区。
4. 源行：文件、行、函数。
5. 全量/指令环：逐条语义。
6. 现场快照：故障寄存器、PC、任务表。

当前：

- 计数、span、采样、源行、原生故障快照已有参考实现。
- 解释器核的 8 个寄存器和栈指针已进入 stop 快照；fault/stop 带 `At` 和 boot/command 作用域。
- 全量/指令环、解释器栈字节、`GuestStack`、全核符号和跨任务源行映射仍未完整。

下一步：

- 把采样时间、采样偏差、源行归属做成可校准的指标。
- 为全量/指令环定义容量、采样率、开销预算和导出格式。
- 故障时自动附加现场快照。

退出：

- 能从命令下钻到函数/指令段，且能说明采样偏差。
- 全量模式有硬上限和关闭开关。

### 3.4 因果与等待

目标：

- 请求/回复、等待/唤醒、队列、依赖、背压。
- 区分排队、传输、执行、呈现。

当前：

- 有调度取走时刻、服务 span、任务 sleep/wake、进程 wait/exit、ZKP1 唯一关联的页面按键→key ring 区间；没有通用请求/回复边。

下一步：

- 在等待/唤醒、信箱、协议请求/回复边界记边。
- 报告能给出依赖链和等待分解。
- 没有边时明确标未覆盖，不靠时间窗推断。

退出：

- 一条慢路径能回答「谁等谁、等了多久、为什么」。
- 因果结论有 E4 证据或明确标候选。

### 3.5 验证语料

语料类型：

- 功能命令、文件操作、进程/调度、显示/输入、错误注入、压力/长跑。
- 每条语料有预期、超时、完成信号和原始输出。

当前：

- 已有 54 条 `/bin` 命令的全量完成语料、受控 runner 和进程级硬超时。
- 故障注入、压力/长跑、交互输入仍不足；语料只验证完成，不比较输出语义。

下一步：

- 把命令当测试向量，建立分类语料库，不把单条命令当目标。
- 为每类语料定义成功标准和回归集。
- 增加负向/边界/并发用例。

退出：

- 任意类别的工作负载都能选到对应语料。
- 回归集覆盖主要边界和关闭状态。

### 3.6 工具与报告

目标：

- 原始数据可导出、可 diff、可复现。
- 报告区分实测/推断/未覆盖。
- 观测开销和丢弃可见。

当前：

- 有文本报告、批次 JSON、日志、检测点清单、capture schema、结构 diff 和验收入口。
- 自动评审仍主要是结构门禁，不解释性能结论。

下一步：

- 定义稳定文本/JSON schema 和版本号。
- 增加报告 diff、覆盖缺口检查、关闭/开销自动测试。
- 把文档一致性检查纳入 `npm test`。

退出：

- 两次会话可直接 diff。
- 报告能自动指出未覆盖和异常丢失。
- 文档与实现不一致时检查失败。

## 4. 推进顺序

1. 标准与治理先稳定；没有标准不扩点。
2. 先补广度：没有检测点的层优先。
3. 再补深度：计数 → span → 采样 → 源行 → 全量。
4. 再补因果：边、队列、依赖。
5. 用语料验证：命令、故障、压力、交互。
6. 每轮都回到标准检查表，不用某次结果替代能力。

## 5. v2 开工资格

ZTrace v2 的完整计划在本地 `dev/Plan/ZTrace-v2.md`，不进入版本库；v2 全量范围包含 2026-11-01 两次审计发现 A1–A15，不以首期范围替代全量范围。进入 v2 实现前必须满足：

| Gate | 条件 | 证据 |
|------|------|------|
| G0 命名与边界 | 产品名 ZTrace；工具侧在 `Compiler/Debugger`；Hardware 实现不动 | 文档和目录评审 |
| G1 基线产物 | 一张干净的 54/54 全量语料 capture，含预期退出码/诊断结果 | `corpus-summary.json`、`gate.json` |
| G2 格式契约 | v2 schema、兼容策略、v1 capture 仍可读 | schema 文档 + 迁移测试 |
| G3 开销与长跑 | 默认开销预算、benchmark、`At` 回绕方案、至少 8 小时 soak | 基准报告 + 长跑 capture |
| G4 深度 | command scope/provenance、全核符号、原生/解释器故障栈、服务内存逐批归属、TaskWait/TaskExit/exitCode | 设计评审 + 小样本 |
| G5 官方集成 | 一条命令采集、诊断包、CI、文档、安全说明 | 集成包评审 |
| G6 设计伙伴 | 3–5 个团队试用，至少 1 个官方链路试点 | 试用记录 + 定位时间对比 |
| G7 发布承诺 | 支持边界、SLO、兼容窗口、责任人 | 发布检查表 |

G1b 的退出传输已改用宿主侧 `ProcessExit`（ZAP 和 native 服务 28 调用点直接读 `home+128`）。全量曾停在 46/54，根因是 VFS 固定路径缓存耗尽；VFS 已扩到 512 项并加满时回收，最终全量 **54/54**、门禁 **8/8**。`--require-exit-codes` 可作为发布门禁。

G4 正在进行：A2/A3 基础已完成，解释器核有 8 个寄存器、栈指针和失败栈字节通道；fault 有 `HostStack`/`GuestStack` 摘要，命令报告只留本次 stop/fault；全量 54/54、门禁 8/8 仍保持。A4（全核符号/构建 ID）和逐帧 `GuestStack` 仍未完成；`StackBytes` 还缺真实命令 fault 样本。

没有 G0–G7 的证据，不进入 v2 功能开发。

## 6. 约束

- 调试设施默认不改协议。线格式以 `Documents/Protocol/` 为准；开发期可在同一协议标识下原位更新正文并记录，发布后要改字段必须先升版本并改协议正文。不加 CPU 指令、不改 19 字任务结构。
- 调试开关关闭时必须惰性。
- 原始 trace 不交给客程序。
- 高频事件用计数/采样，不逐条写环。
- 采样、估算、未覆盖必须标注。
- 一次只改一个变量；没有可重复收益就回退。
- 本地工作，不因调试新增大量提交或 tag。

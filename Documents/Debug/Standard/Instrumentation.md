# 观测设计标准

## 1. 目的

本文件规定调试观测点的设计、覆盖、开销和验证要求。它不绑定某个设备或某次实现。

观测设施的目标是：任意子系统、任意路径都能被同一套语义观察，而不是为某条命令临时插探针。

## 2. 设计顺序

1. 定义要回答的问题。
2. 画出现有边界：线程、进程、设备、队列、共享内存、协议。
3. 标出已有可观测边界。
4. 选择级别：计数、事件、span、边、采样、全量、快照。
5. 定义字段、单位、父子/边关系。
6. 评估频率、数据量、开销和关闭行为。
7. 写验证用例：已知答案、边界、关闭、溢出。
8. 更新检测点清单和覆盖矩阵。

## 3. 观测点分类

| 类型 | 位置 | 例子 |
|------|------|------|
| 生命周期 | 创建/销毁/挂载/卸载 | 任务、设备、页、连接 |
| 边界 | 系统调用、消息、协议、函数入口/出口 | svc、exchange、请求/回复 |
| 状态转换 | 就绪/运行/等待/停止 | 调度、队列、锁 |
| 资源 | 分配/释放/容量/水位 | 内存、句柄、缓冲 |
| 传输 | 字节、端口、方向、批次 | 设备 I/O、NAS、GPU |
| 错误 | 失败、超时、拒绝、越界 | fault、停机、协议错误 |
| 进度 | 阶段、里程碑、完成 | 启动、安装、命令 |
| 现场 | 寄存器、PC、栈、任务表 | 故障快照 |

覆盖要求：

- 每个子系统至少有一个生命周期或边界点。
- 每个等待/唤醒关系至少有一侧记录，最好有边。
- 高频路径优先计数/采样，不逐条写环。
- 没有点的路径在覆盖矩阵写「未覆盖」。

## 4. 记录模型

逻辑字段：

| 字段 | 要求 |
|------|------|
| 时间 | 单调时钟，单位明确 |
| 类型 | 计数/事件/span/边/采样/快照 |
| 层 | 宿主/核心/协议/系统调用/调度/客程序 |
| 身份 | 核、任务、进程、设备、端口 |
| 操作 | 稳定的事件码/名字 |
| 参数 | 字节数、状态、原因、序号 |
| 关系 | span/parent 或 edge 起点/终点 |
| 标志 | 采样/全量、原生/ZAP、错误 |
| 版本 | 记录 schema 版本 |

要求：

- 定长记录，环内不存变长字符串。
- 开始/结束按稳定编号配对，不靠时间窗猜。
- 无法确定父时留空，报告标为未归类。
- 写入顺序保证读方不会读到半条记录。
- 事件名稳定、小写、点分；改名视为 schema 变更。

## 5. 开关与开销

- 总开关必须唯一；关闭时不分配环、不读时钟、不写记录、不发消息。
- 每个入口一次判断，不在每条事件里做字符串格式化。
- 高频事件用计数或采样；采样规则写入文档。
- 环有界；满时覆盖最旧并记录 `dropped`。
- 观测开销必须可测：同一实验开/关各跑，记录差异。
- 关闭状态必须有负向测试：零记录、零新页、零入口。

## 6. 广度与深度

广度：所有子系统、所有边界、所有错误路径至少有一个点。

深度：从命令/请求到设备/指令的链路可以逐层下钻，至少包含：

- 决策级：命令、请求、任务。
- 传输级：消息、端口、字节。
- 执行级：线程、函数、采样、指令。
- 因果级：等待、唤醒、依赖。

只有广度没有深度：知道哪个设备慢，不知道哪条路径。
只有深度没有广度：能解释一个点，不能推广。

## 7. 验证用例

每个观测点至少验证：

1. 已知答案：构造一个可预测的事件，字段和计数正确。
2. 边界：空、满、越界、重复、并发。
3. 关闭：开关关闭时零写入。
4. 溢出：环满时覆盖和 `dropped` 正确。
5. 跨线程：时钟、父子、序号一致。
6. 采样：采样间隔和偏差可解释。
7. 开销：开启后不改变被测语义；开销在预算内。
8. 版本：符号/源行/调试表必须与被测二进制同一次构建；旧表比没有表更危险。

## 8. 评审清单

- 这个点回答什么问题？
- 它属于哪一类边界？
- 频率多少？最坏情况多少条/秒？
- 记录多大？环能撑多久？
- 有父/边吗？没有时报告怎么标？
- 关闭时真的惰性吗？
- 数据是否包含敏感内容？
- 如何用已知答案验证？
- 覆盖矩阵和检测点清单是否更新？
- 消费者是谁？报告还是原始导出？

## 9. 反模式

- 为一条命令新增专用探针。
- 把原始 trace 暴露给客程序。
- 用时间窗推断父子关系。
- 每条访存/每条指令都写环。
- 采样后仍按全量口径汇报。
- 关闭开关后仍读旧页。
- 只加写入点，不更新覆盖和验证。
- 为了报告好看修改事件语义。
- 每次构建都无条件生成大体积调试副本，或复用与二进制不同版本的源行表。
